# Agentonomous — Agent-Proof Production Foundation (Increment 4)

## 1. Purpose & Scope

Increments 1-3 built a framework with shell/core split, module system, typed EventBus, structured logging, and three observability modules. Increment 4 hardens the framework into an **agent-proof production foundation** — structural quality mechanisms that ensure code generated by AI agents is correct-by-construction.

**In scope (8 items)**
1. Graceful module degradation (try/catch around module init)
2. Shared test fakes (canonical FakeLogger, FakeSettings, etc.)
3. Settings migration framework (settingsVersion + migrate())
4. Cross-module import ban (ESLint rule)
5. emitAsync backpressure (per-call maxConcurrency)
6. EventBus listener introspection (listenerCount + leak detection)
7. max-lines → error for domain/modules (ESLint)
8. JSDoc on Module interface

**Out of scope**
- Module scaffold script / wizard (deferred to a later increment as a plugin command)
- Obsidian API version guard (built into Obsidian itself)
- Release pipeline (deferred to pre-marketplace submission)
- Business-logic modules

## 2. Graceful Module Degradation

`PluginCore.init()` wraps each `module.init(ports, settings)` in a try/catch.

**On failure:**
- Log at `error`: `"Module ${module.id} failed to initialize: ${message}"`
- Emit `core` event with `phase: 'validation', degraded: true, errors: [message]`
- Skip the failed module — do NOT register its commands
- Continue initializing remaining modules
- `core:ready` emits with `degraded: true` if any module failed
- `PluginCore.ready` is still `true` (plugin works with fewer modules)
- `PluginCore.degradedModules: readonly string[]` getter exposes failed module IDs

**Destroy path:** skips modules that never initialized (tracked via a `Set<string>` of successfully initialized module IDs).

**Notification:** `ErrorHandler` sees the `core` event with `degraded: true` and shows a Notice: `"Agentonomous: module [id] failed to load — running in degraded mode"`.

## 3. Shared Test Fakes

Create `tests/__fakes__/fake-ports.ts` with canonical implementations:


Each returns `vi.fn()`-backed mocks with sensible defaults. `fakeModulePorts()` composes all of them into one `ModulePorts` bag — the standard way to set up module tests.

## 4. Settings Migration Framework

### 4.1 Module interface additions

```ts
interface Module {
    // ... existing fields ...
    readonly settingsVersion?: number;
    migrate?(fromVersion: number, blob: unknown): Result<unknown, string>;
}
```

Both fields are optional. Modules that don't declare `settingsVersion` skip migration entirely.

### 4.2 Persisted settings shape

Each module's settings section gains a `_version` field:

```json
{
    "core": { "_version": 1, "showRibbonIcon": true, "defaultView": "home", "logLevel": "info" },
    "eventInspector": { "_version": 1, "enabled": true, "maxEvents": 500, "filterChannels": [] }
}
```

`_version` is managed by `PluginCore`, not by the module. Modules read/write their own fields; core manages `_version`.

### 4.3 Migration flow at startup

1. Load raw blob via `SettingsPort.load()`.
2. For each module with `settingsKey` + `settingsVersion`:
   - Extract `raw[module.settingsKey]`.
   - Read `section._version` (default `0` if missing — handles first-time load).
   - If `section._version < module.settingsVersion` AND `module.migrate` exists:
     - Loop: call `module.migrate(currentVersion, section)` → get migrated blob → increment version → repeat until versions match.
     - On migration error → log at `warn`, fall back to `module.settingsDefaults`.
   - If `section._version === module.settingsVersion` → use as-is (after validation).
   - If `section._version > module.settingsVersion` → log at `warn` (downgrade detected), use as-is.
3. Save the migrated blob back via `SettingsPort.save()` so future loads skip migration.

### 4.4 `defineModule` builder update

`defineModule<T>()` gains optional `settingsVersion` and `migrate` fields in its parameter type, matching the base `Module` interface.

## 5. Cross-Module Import Ban

ESLint rule in `configs/eslint.config.mjs`:

```js
{
    files: ['src/modules/**/*.ts', 'src/modules/**/*.vue'],
    rules: {
        'no-restricted-imports': ['error', {
            patterns: [{
                group: ['**/modules/*/*'],
                message: 'Modules must not import from other modules — use EventBus for cross-module communication',
            }],
        }],
    },
},
```

Modules may import from `src/domain/**` (ports, types, utilities) and `src/core/**` (Logger, ErrorHandler types). They must NOT import from sibling modules.

**Exception:** the existing `src/modules/` ESLint block already has `no-console: 'off'` and `no-restricted-syntax: 'off'`. The new `no-restricted-imports` rule is added to the same block (merged rules object).

## 6. emitAsync Backpressure

### 6.1 API change

```ts
emitAsync<K extends keyof EventMap>(
    channel: K,
    payload: EventMap[K],
    opts?: {
        parentId?: string;
        maxConcurrency?: number;  // default: Infinity (current behavior)
    },
): Promise<EventEnvelope<K>>;
```

### 6.2 Implementation

A concurrency-limited executor runs listener tasks in a pool:

```ts
async function runWithConcurrency(
    tasks: (() => void | Promise<void>)[],
    limit: number,
): Promise<void> {
    if (!Number.isFinite(limit)) {
        await Promise.all(tasks.map((t) => t()));
        return;
    }
    let index = 0;
    async function next(): Promise<void> {
        while (index < tasks.length) {
            const i = index++;
            await tasks[i]();
        }
    }
    await Promise.all(
        Array.from({ length: Math.min(limit, tasks.length) }, () => next()),
    );
}
```

This is a standard worker-pool pattern. Sync listeners return `void` and complete immediately; async listeners occupy a pool slot while awaiting. `onAny` listeners run after all channel listeners complete (same as current behavior).

### 6.3 Backward compatibility

Default `maxConcurrency` is `Infinity`, so all existing `emitAsync` calls behave identically. The opt-in nature means no existing code is affected.

## 7. EventBus Listener Introspection

### 7.1 API addition

```ts
interface EventBus {
    // ... existing methods ...
    listenerCount(channel?: keyof EventMap): number;
}
```

- No argument: returns total listeners across all channels + `onAny` listeners.
- With channel: returns count for that specific channel only.

### 7.2 Leak detection in PluginCore.destroy()

Before destroying each module, `PluginCore` snapshots `bus.listenerCount()`. After `module.destroy()`, it checks the delta:

```ts
const before = bus.listenerCount();
module.destroy();
const after = bus.listenerCount();
if (after >= before) {
    logger.warn('core', `Module "${module.id}" may have leaked ${after - before + 1} event listener(s)`);
}
```

This is a best-effort heuristic — it catches the common case where a module subscribes in `init()` but forgets to unsubscribe in `destroy()`. False positives are possible if another module concurrently subscribes during the destroy sequence, but the `warn` level ensures it's non-blocking.

## 9. JSDoc on Module Interface

Add JSDoc to every field of `Module` and `ModulePorts` in `src/domain/shared/module.ts`:

```ts
interface Module {
    /** Unique identifier across all registered modules. Duplicates are fatal at startup. */
    readonly id: string;

    /** Human-readable name for logs, settings UI, and health reports. */
    readonly name: string;

    /** Module IDs that must complete init() before this one. Circular deps are fatal. Unknown deps are fatal. */
    readonly dependsOn?: readonly string[];

    /** Key in the merged settings blob. Must not collide across modules. Omit for modules with no settings. */
    readonly settingsKey?: string;

    /** Default settings used when no persisted data exists or validation fails. */
    readonly settingsDefaults?: unknown;

    /** Schema version for settings migration. Increment when the settings shape changes. */
    readonly settingsVersion?: number;

    /** Validates raw persisted settings blob. Return ok(validated) or err(reason). On err, defaults are used. */
    validateSettings?(raw: unknown): Result<unknown, string>;

    /** Migrates settings from an older version. Called in a loop until version matches settingsVersion. */
    migrate?(fromVersion: number, blob: unknown): Result<unknown, string>;

    /** Commands to register with Obsidian. Declared as data; PluginCore handles registration. */
    readonly commands?: readonly CommandEntry[];

    /** Called after dependencies are ready. Receives scoped ports and validated settings. May subscribe to EventBus. */
    init(ports: ModulePorts, settings: unknown): Promise<void>;

    /** Called on plugin unload in reverse dependency order. Must unsubscribe all listeners and clear intervals. */
    destroy(): void;
}
```

Also add JSDoc to `defineModule<T>()`:

```ts
/**
 * Type-safe module builder. Preserves TSettings at the definition site for compile-time safety,
 * then erases to Module (with unknown settings) for the heterogeneous collection in PluginCore.
 *
 * This is the required way to create modules. Direct Module object literals will lose type safety.
 */
export function defineModule<TSettings = unknown>(def: { ... }): Module;
```

And to `ModulePorts`:

```ts
interface ModulePorts {
    /** Typed pub/sub for cross-module communication. The only sanctioned way to interact with other modules. */
    readonly eventBus: EventBus;
    /** Structured logger (debug/info/warn/error). Dual console + bus output. */
    readonly logger: LoggerPort;
    /** Load/save the merged settings blob. Modules should only read their own settingsKey section. */
    readonly settings: SettingsPort;
    /** Show user-facing toast notifications. Use for user-severity errors only. */
    readonly notifications: NotificationPort;
    /** Register and open Obsidian views. */
    readonly views: ViewRegistryPort;
}
```

## 10. Acceptance Criteria

1. A module that throws in `init()` does not crash the plugin — verified by a test that injects a throwing module alongside healthy ones and asserts the healthy ones still initialize.
2. `PluginCore.degradedModules` returns the IDs of failed modules.
3. All test files use `fakeModulePorts()` from `tests/__fakes__/fake-ports.ts` — no inline mock construction remains.
4. Settings with `_version: 0` when module declares `settingsVersion: 1` → `migrate()` is called and the result is persisted.
5. `src/modules/foo/` importing from `src/modules/bar/` → ESLint error (verified by a linting test or by adding a probe file).
6. `emitAsync('tick', payload, { maxConcurrency: 2 })` with 5 async listeners → at most 2 run concurrently (verified by tracking concurrent-execution count in a test).
7. `bus.listenerCount('core')` returns correct count; `PluginCore.destroy()` warns on leaks (verified by a module that deliberately doesn't unsubscribe in destroy).
8. A 351-line file in `src/domain/` or `src/modules/` fails `npm run lint`.
9. `Module` interface has JSDoc on every field — verified by `npm run docs` generating meaningful TypeDoc output.
10. `npm test` green, coverage ≥ 80/70/80/80.

## 12. Risks

- **Settings migration loop** — a buggy `migrate()` that doesn't advance the version causes an infinite loop. Mitigated by capping the loop at `module.settingsVersion - currentVersion` iterations and breaking with an error if the version doesn't advance.
- **Shared fakes coupling** — changing a fake's default behavior affects all tests. Mitigated by `fakeModulePorts(overrides)` accepting partial overrides so tests can customize without rewriting the base.
- **Cross-module import ban false positives** — modules importing from `src/domain/` via a path that traverses `src/modules/` (unlikely but possible with misconfigured paths). Mitigated by testing the rule with a probe file.
