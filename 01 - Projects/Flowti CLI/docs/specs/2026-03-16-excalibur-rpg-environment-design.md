# Excalibur RPG Environment — Live Agent World

**Date**: 2026-03-16
**Status**: Approved
**Scope**: Transform the static ExcaliburJS agent dashboard into a live RPG world with goal-oriented movement, interactive panels, and full agent control
**Iteration**: 5 — Agent World (Phase B)

## Problem

Agents have a rich data model — GURPS attributes, personas, moods, personality traits, goals, behaviors, relationships, experience — but the current ExcaliburJS dashboard renders them as colored circles in a static grid. The grid shows status (busy/idle/unassigned) and nothing else. The RPG character model is invisible. There is no interaction: you cannot talk to agents, assign tasks, or approve permissions from the game. The dashboard reads a snapshot JSON file that is regenerated on server start — there are no live updates.

The CLI already has all the infrastructure: `WorldStateManager` with ECS entities and the full set of agent action types, `WorkerManager` with persistent reactive workers, per-agent conversation persistence, a decision engine with LLM and NPC backends, and a static HTTP server. The missing piece is connecting this live backend to the game engine so agents become visible characters in an interactive world.

## Decision

### Architecture: Hybrid Client

The CLI is the single source of truth for **data** (agent state, tasks, permissions, world state). The game is the authority for **presentation** (positions, movement paths, animation states, workstation occupancy). The game maintains a local `AgentBrain` state machine per agent that drives movement and visual behavior based on the latest world state data. When the user interacts (send message, assign task, grant permission), the game fires an HTTP request to the CLI and optimistically updates the visual — then reconciles when the CLI responds.

The game never invents data state (it does not decide an agent is "busy"). It does invent presentation state (it decides where the agent walks, what animation plays, when idle quotes appear).

### Data Flow — Three Channels

**Channel 1 — State Snapshot (poll, every 30s)**

Game fetches `GET /api/world-state` from the server. This is a dedicated API route (not a static file) because `world-state.json` lives at `.flowti/var/world-state.json`, outside the static server's root directory. The handler reads the file on each request, guaranteeing fresh data without a regeneration cadence. Returns the full `WorldState` with all entities, permissions, and activity log. The game diffs against its local copy — new entities spawn, removed entities despawn, changed components trigger visual transitions.

Note: the existing `data/agent-dashboard.json` (generated by `regenerateDashboardData` on server start) is still used for the initial boot — it contains the enriched `DashboardAgent` data with RPG fields. The game loads it once on connect for the agent roster, then switches to `world-state.json` polling for live state.

**Channel 2 — Action Events (SSE, real-time)**

New endpoint `GET /events` on the static server. The `WorldStateManager` pushes each `AgentAction` as a Server-Sent Event:

```
event: agent-action
data: {"id":"...","agentName":"Bob","type":"using-tool","timestamp":"...","data":{"tool":"Edit"}}
```

Entity-level updates use a separate event type:

```
event: entity-update
data: {"id":"Bob","type":"agent","components":{"status":{"state":"busy"}}}
```

The game subscribes via `EventSource` on connect and maps each action to an immediate visual response. If SSE disconnects, the game falls back to poll-only (every 5s) until reconnect. Reconnection uses exponential backoff (1s, 2s, 4s, 8s, 16s, 30s cap).

**Channel 3 — Commands (HTTP POST, user-initiated)**

New endpoints on the static server:

| Endpoint | Body | Effect |
|---|---|---|
| `GET /api/world-state` | — | Returns current `WorldState` from `.flowti/var/world-state.json` (read on each request). |
| `POST /api/agent/send` | `{ agentName, message }` | Routes to `workerManager.send()`. Returns `{ ok: true }`. Response arrives via SSE. |
| `POST /api/agent/task` | `{ agentName, task, source? }` | Full cycle: `readAgentState()` from `.flowti/var/`, call `addTask(state, task)` to produce new state, `writeAgentState()` to persist, then `worldState.emitAction()` with a `task-started` action. Task comes from `suggestedTasks` (matched by name) or freeform text. For AI agents, the emitted `task-started` action triggers the decision engine's `task-assigned → execute-task` rule via `dispatchWorldEvent`, which spawns an LLM process. The game shows a confirmation dialog before assigning to AI agents: "This will start an AI session. Continue?" Returns `{ ok: true, taskId }`. |
| `POST /api/agent/permission` | `{ agentName, tool, decision }` | Updates permission entry if still pending (idempotent — if already resolved, returns `{ ok: true, alreadyResolved: true }`). Emits `permission-granted` or `permission-denied`. Returns `{ ok: true }`. |
| `GET /api/agent/:name` | — | Returns full agent entity from world state (components, permissions, recent activity). |

The static server gains a thin API layer. No business logic in the API handlers — they call existing domain functions through `CliDeps`.

### Scene Architecture — Hub & Rooms

**Hub Scene** — central overview showing all agents as small characters grouped loosely by domain. Doorways on the edges lead to themed rooms. Neutral dark theme (`#0a0a0f`).

Hub elements:
- Agent characters (small scale, name labels)
- Status indicators (busy glow, idle dim)
- Three doorways labeled by setting (Office, Village, Station)
- Activity ticker along the bottom (last 5-10 activity log entries scrolling)
- Iteration context badge (current iteration name + progress)

**Room Scenes** — three themed environments:

| Setting | Domain mapping | Visual theme | Workstation type |
|---|---|---|---|
| **Office** | engineering, qa, devops | Gray/blue, desks, monitors | Desk with terminal |
| **Village** | design, ux, product | Earth tones, crafting tables | Workbench/easel |
| **Station** | management, delivery, coordination | Neon/cyan, consoles | Command console |

Domain mapping is configurable in `domain-map.ts`, not hardcoded. An agent's `domain` field determines their home room. Agents without a domain default to the hub.

**Navigation:** Click a doorway to enter a room. Press Escape or click a back element to return to the hub. Agents in a room that you are not viewing still animate — their brain runs regardless of which scene is active.

**Agent presence:** An agent's character appears in their home room when they have active work. Idle agents may wander to the hub. When you enter a room, you see agents at workstations (busy), wandering (idle), or clustered near collaborators.

### Agent Visual

Replacing the current circle-and-icon with a canvas-drawn character:

- Simple humanoid silhouette (head circle + body rectangle + limbs) — no sprites, no asset files
- Colored by visual status derived from two sources: the `DashboardAgent.status` field (`busy`, `idle`, `unassigned`) for the base color, and the world state entity's `components.status.state` for the `waiting` state (which exists in `WorkerState` but not in `AgentStatus`). Mapping: green tint (busy), blue tint (idle), gray (unassigned), amber (waiting — derived from `components.status.state === "waiting"`)
- Persona name label below
- Type badge above (AI/H, small text)
- Mood indicator: facial expression on the head circle (`:)` cheerful, `:|` neutral, `>:|` vigilant, `?` confused) derived from the `mood` field
- Direction facing: character flips horizontally based on movement direction

### Agent Brain — Pure State Machine

External to the actor, the `AgentBrain` drives movement and visual behavior. It is a pure function: `(currentState, event, attributes) → nextState + movementTarget`.

**States:**

| State | Behavior |
|---|---|
| `idle` | Wander randomly, occasionally show idle quote bubble |
| `wandering` | Walking to a random point in the room |
| `walking-to` | Moving purposefully to a target (workstation, agent, doorway) |
| `working` | Seated at workstation, small animation loop (typing, crafting, operating) |
| `talking` | Facing another agent or the camera, speech bubble visible |
| `waiting` | Standing still, question mark bubble, pulsing glow |

**Transitions driven by world state actions:**

| Action | Transition |
|---|---|
| `task-started` | `idle`/`wandering` → `walking-to` workstation → `working` |
| `task-completed` | `working` → `idle` |
| `speaking` | → `talking` (face toward nearest agent or camera) |
| `thinking` | → `working` (thought bubble at workstation) |
| `asking` | → `waiting` (question bubble) |
| `using-tool` | → `working` (tool name shown above workstation) |
| `idle` | → `idle` (leave workstation, start wandering) |
| `permission-granted` | `waiting` → `working` |
| `permission-denied` | `waiting` → `idle` |

**Attribute influence on behavior:**

| Attribute | Effect |
|---|---|
| **DEX** | Movement speed (0.5x to 1.5x scale from 1-20 range) |
| **CHA** | Wander radius toward other agents (high CHA = social, clusters near others) |
| **INT** | Time spent at workstation before wandering (high INT = longer focus) |
| **CON** | Less frequent idle state transitions (high CON = endurance) |
| **WIS** | Idle quote frequency (high WIS = more philosophical idle quotes) |
| **STR** | Reserved for future use |

### Click-to-Interact — HTML Overlay Panel

Clicking an agent pauses their wandering and opens an HTML overlay panel anchored to the agent's screen position. The panel is a DOM element layered over the canvas — standard HTML/CSS for forms, scrollable lists, and text input.

**Panel layout:**

```
┌─────────────────────────────────────┐
│  Bobby (AI)            [×]          │
│  "cheerful, curious"                │
│  ─────────────────────────────────  │
│  Status: working — Edit src/main.ts │
│  Mood: cheerful  XP: 150            │
│                                     │
│  STR 8  INT 14  WIS 12              │
│  CHA 16 DEX 10  CON 10              │
│  ─────────────────────────────────  │
│  Tasks (2)                          │
│  ● Fix auth bug        [in-progress]│
│  ○ Write tests          [pending]   │
│  ─────────────────────────────────  │
│  [Talk]  [Assign Task]  [Permissions]│
│  ─────────────────────────────────  │
│  Conversation                       │
│  You: How's the auth fix going?     │
│  Bobby: I've identified the issue...│
│  ┌─────────────────────────┐        │
│  │ Type a message...    [→]│        │
│  └─────────────────────────┘        │
└─────────────────────────────────────┘
```

**Panel tabs:**

| Tab | Content | Data source |
|---|---|---|
| **Info** (default) | Attributes, mood, status, skills, relationships | Local from world state entity |
| **Talk** | Conversation thread + input | `POST /api/agent/send` — response arrives via SSE |
| **Tasks** | Task queue + assign from `suggestedTasks` (filtered by current iteration phase — only show tasks whose `phases` array includes the active phase, or all if `phases` is empty) | `POST /api/agent/task` |
| **Permissions** | Pending requests + grant history | `POST /api/agent/permission` |
| **History** | Recent activity log filtered to this agent | Local from world state activity log |

**Optimistic updates:** When you send a message, the panel immediately shows "You: ..." and the agent transitions to `talking`. The response arrives via SSE (`speaking` action) and updates both the speech bubble and the thread. NPC responses are near-instant (`respondFromState`). AI responses show a thinking bubble while the LLM works.

**Permission flow in-game:** When an agent emits `requesting-permission`, they enter `waiting` with a lock icon. Their panel auto-opens to the Permissions tab if you are in the same room. You click Allow/Deny. The game posts to `/api/agent/permission`, the agent transitions to `working` or `idle`.

### Live Update Event Mapping

Each SSE event maps to an immediate game reaction:

| SSE event | Game reaction |
|---|---|
| `thinking` | Show thought bubble, brain → `working` |
| `speaking` | Show speech bubble with text, brain → `talking` |
| `using-tool` | Show tool name above workstation, brain stays in `working` |
| `tool-complete` | Clear tool name (visual-only, no brain state transition) |
| `task-started` | Brain → `walking-to` workstation → `working` |
| `task-completed` | Brain → `idle`, leave workstation |
| `requesting-permission` | Brain → `waiting`, lock icon, auto-open panel if in room |
| `permission-granted` | Brain → `working`, lock clears |
| `permission-denied` | Brain → `idle`, lock stays briefly then clears |
| `asking` | Brain → `waiting`, question bubble |
| `idle` | Brain → `idle` |
| `error` | Flash red, alert icon, brief error bubble |
| `entity-update` | Diff components, update visuals (mood, status, task list) |

**Poll reconciliation (every 30s):**
- New entity → spawn character in appropriate room
- Removed entity → despawn with fade-out
- Changed components → update brain state, visuals, panel data if open
- Activity log → update hub ticker

**Connection status:** A small "LIVE" / "POLLING" indicator in the corner. LIVE when SSE connected, POLLING when in fallback mode.

Read-only expansion. The game consumes it, never writes back.

### `static-server.ts` — Routing Layer + API Endpoints + SSE

The current `handleRequest` is a pure function returning `ServeResult` — it has no access to the raw `ServerResponse` (needed for SSE keep-alive) or request body (needed for POST). The `createServer` callback in `startServer` must be restructured with a routing layer that intercepts API routes before they reach `handleRequest`:

1. Check if the URL starts with `/events` or `/api/` — if so, dispatch to the API handler
2. Otherwise, fall through to the existing `handleRequest` for static files

The API handler is a new function that receives the raw `req`/`res` plus a `ServerContext` containing `workerManager`, `worldState`, and `deps`. This keeps `handleRequest` pure (no breaking change) while the routing layer handles the new concerns.

```typescript
interface ServerContext {
	readonly worldState: IWorldStateManager;
	readonly workerManager: IWorkerManager;
	readonly deps: Pick<CliDeps, "disk" | "paths" | "clock">;
	readonly sseClients: Set<ServerResponse>;
}
```

Routes:
- `GET /events` — SSE endpoint. Sets `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`. Adds `res` to `sseClients` set. On connection close, removes from set.
- `GET /api/world-state` — reads `.flowti/var/world-state.json` via `deps.disk`, returns JSON.
- `POST /api/agent/send` — parse JSON body via `req.on("data")`, call `workerManager.send()`, return `{ ok: true }`.
- `POST /api/agent/task` — parse JSON body, assign task, return `{ ok: true, taskId }`.
- `POST /api/agent/permission` — parse JSON body, update permission (idempotent), return `{ ok: true }`.
- `GET /api/agent/:name` — return full agent entity from world state.

All requests are same-origin (game and API served from the same port), so no CORS headers are needed. If a future dev server scenario requires cross-origin, CORS headers can be added to the routing layer without touching `handleRequest`.

The `ServeDeps` interface does not change. The `ServerContext` is constructed in `dashboard-service.ts` and passed to `startServer` as a new optional parameter. Note: `ServerContext.deps` includes `clock` (for timestamping task creation and permission grants) — this is a new dependency for the API layer, not inherited from `ServeDeps`.

### `dashboard-service.ts` — Wire SSE Callback

When the dashboard server starts, register a callback on `WorldStateManager` that pushes actions to all connected SSE clients. Maintain a `Set<ServerResponse>` of active SSE connections. On action, iterate and write to each. On connection close, remove from set.

### `world-state-manager.ts` — Multiple Callbacks + STATUS_MAP Fix

Replace `setActionCallback(callback)` with `addActionListener(callback)` and `removeActionListener(callback)`. Internal storage changes from a single nullable callback to an array of callbacks. All registered listeners are called on each action.

The existing call in `deps.ts` (line ~114) that wires `worldState.setActionCallback((action) => workerManager.dispatchWorldEvent(action))` must be updated to use `addActionListener`. The SSE publisher in `dashboard-service.ts` registers a second listener when the server starts, and removes it when the server stops.

The `IWorldStateManager` interface in `world-state-types.ts` replaces `setActionCallback` with the new methods. `setActionCallback` is removed entirely (not deprecated) since only one call site uses it (`deps.ts`) and it changes in the same commit.

**STATUS_MAP correction:** The current `STATUS_MAP` maps `permission-denied` to `{ state: "waiting", currentAction: "permission-denied" }`. This conflicts with the brain's expected behavior where `permission-denied` transitions the agent to `idle`. Update the `permission-denied` entry to `{ state: "idle", currentAction: "permission-denied" }` so the world state and game brain agree. Without this fix, poll reconciliation would see `state: "waiting"` and re-derive the visual as amber, contradicting the brain's `idle` state.

## Design Choices

| Decision | Choice | Rationale |
|---|---|---|
| Architecture | Hybrid — CLI owns data, game owns presentation | Clean separation. CLI never cares about positions. Game never invents business state. |
| Character rendering | Canvas-drawn silhouettes | Zero asset dependencies. Consistent with CLI's zero-runtime-deps philosophy. |
| Panel implementation | HTML overlay | ExcaliburJS has limited UI primitives. HTML gives text input, scrollable lists, CSS styling. |
| Brain state machine | Pure function external to actor | Testable without ExcaliburJS. Composable. |
| Scene structure | Hub-and-rooms with doorways | Overview + immersion. See all agents or dive into themed rooms. |
| Domain mapping | Configurable | Users define custom domains. Defaults cover common cases. |
| Live updates | SSE + poll dual channel | Real-time action animations + guaranteed state consistency. |
| Reconnection | Exponential backoff, poll fallback | Standard resilience pattern. Game stays useful without SSE. |
| Workstation occupancy | One agent per station, first-come | Avoids visual overlap. Overflow agents work standing. |
| Speech bubbles | FIFO queue, max 3 visible, 5s auto-dismiss | Prevents bubble spam during fast SSE streams. |
| Idle quotes | From personality + mood, 15-30s interval | Makes agents feel alive. Frequency scales with WIS attribute. |
| Agent room transition | Walk to doorway → despawn → respawn | Smooth visual when domain changes or agent reassigned. |
| Room scaling | Grid workstations, 4 columns, scroll if >16 | Handles large teams gracefully. |
| CLI exit | "Disconnected" overlay, all polling stops | No zombie connections. Restart `flowti serve` to reconnect. |
| Panel during scene switch | Auto-close | Prevents orphaned panel anchored to actor in different scene. |

## Edge Cases

- **Concurrent CLI sessions:** Only one CLI process writes `world-state.json`. Multiple browser tabs can connect to SSE — each gets its own connection. No browser-side conflicts since the game is read-only for data state.
- **Agent without domain:** Defaults to hub scene. Appears in the hub with other unassigned agents.
- **Agent domain changes:** On next poll reconciliation, agent walks to doorway in current room, despawns, respawns in new room.
- **SSE flood (many rapid actions):** Bubble queue caps at 3 per agent. Brain transitions debounce — intermediate states may be skipped visually (e.g., `thinking` → `speaking` within 100ms skips the thinking bubble).
- **NPC vs AI interaction:** Identical visual treatment. NPC responses arrive near-instantly via SSE. AI responses show thinking bubble during LLM processing. The panel and brain do not distinguish. Implementation note: the current `processNpcMessage()` in `worker-manager.ts` calls `opts.onResponse` but does not emit a `speaking` world state action. The `POST /api/agent/send` handler must emit a `speaking` action after receiving the NPC response so the SSE channel delivers it to the game. This is a small addition to the API handler, not a change to `worker-manager.ts`.
- **Empty world state:** Hub renders with no agents, doorways still visible. "No agents defined" message in center.
- **Dashboard build missing:** `buildDashboard()` already handles this — checks for output, installs deps, builds. No change needed.
- **Large conversation history:** Talk tab shows last 20 turns (scrollable). Older turns exist in the conversation file but are not rendered. Conversation persistence (per-agent JSON files in `.flowti/var/conversations/`) already exists in `agent-conversation-store.ts`. Note: `worker-manager.ts` does not currently read/write conversation history (it passes `[]` for history). The `POST /api/agent/send` handler must load conversation history via `loadConversation()`, include prior turns in the prompt, and save the new turn via `saveConversation()` — mirroring what the Talk menu (`agents-interact-menu.ts`) already does.
- **Same-origin serving:** The game and API are served from the same port by the same HTTP server. No CORS headers are needed. If a future dev server scenario requires cross-origin, CORS headers can be added to the routing layer.
- **Duplicate permission grants:** If two browser tabs both click "Allow" for the same pending permission, the second request sees the permission is already resolved and returns `{ ok: true, alreadyResolved: true }` without re-emitting the action.
- **Task assignment to AI agents:** Assigning a task from the game panel triggers the decision engine's `task-assigned → execute-task` rule, which spawns an LLM process. The Tasks tab shows a confirmation dialog before assigning to AI agents: "This will start an AI session. Continue?"
- **Panel anchor during camera movement:** Each room scene uses a fixed camera (no pan/zoom) — the camera shows the entire room at once. The panel anchor position is set once when opened and does not need per-frame updates. If rooms later gain camera movement, the panel manager will need a `scene.onPostUpdate` hook to track screen-space coordinates.
